MTFWBuilder

MTFWBuilder

Overview

MTFWBuilder is a self-hosted web application for Meshtastic radios. The operator fills in a form. The project writes a userPrefs.jsonc file from the form. The project then compiles Meshtastic firmware with PlatformIO, and the userPrefs.jsonc values are compiled into the firmware. The operator downloads the firmware and flashes it to the device.

The project serves three groups:

  • the owner, who runs it in a homelab for personal devices;
  • self-hosters in the Meshtastic community, who clone the repository and run it;
  • event and fleet organizers, who give many devices the same channels and settings.

The official Meshtastic Web Flasher flashes prebuilt firmware only. The Meshtastic CLI configures a device after it is flashed. No other public tool gives a web interface for firmware that carries custom defaults. Research on 2026-11-21 found only small command-line forks (see pages/inherit-reconciliation.md).

Current state (2026-11-21). The v2 rewrite (FastAPI, March 2026) changed the backend. It did not change the frontend. Research found that the end-to-end flow does not work today, for these reasons:

  • The pages call v1 URLs that the v2 backend does not serve.
  • 71 of the 150 registry ids are not PlatformIO environment names.
  • Upstream firmware changed its output file names in December 2025.
  • The generator writes many keys that the firmware does not read.

This spec documents the code as it is (status: built features 01–04). It then plans the repair, the update to current upstream firmware, and new capabilities (status: planned features 00 and 05–15). The full reconciliation of documents against code is in pages/inherit-reconciliation.md.

An important upstream fact. A userPrefs.jsonc value is a factory default. The firmware applies it on first boot and on factory reset only. After that, the saved device config wins. To stop a user changing settings, the config must set an admin key (USERPREFS_USE_ADMIN_KEY_0) and USERPREFS_CONFIG_SECURITY_IS_MANAGED. Source: the header of userPrefs.jsonc in meshtastic/firmware develop@fe89ac1.

Goals

  1. An operator makes a config, starts a build, and downloads a working artifact for any

release or pr variant of the selected firmware version.

  1. Every userPrefs key the project writes is a key the selected firmware version reads.

A test checks this against the firmware source.

  1. The registry comes from the firmware source. No person edits a variant list by hand.
  2. The config form covers every userPrefs key that upstream lists, except the keys in

Non-goals.

  1. An operator flashes an ESP32-family artifact from the browser in one step.
  2. An organizer makes builds for 20 devices in one fleet run.
  3. No secret stays on disk after its build ends, on any path: success, failure, timeout

or cancel.

  1. A fresh clone installs, tests, lints and starts with the commands in CLAUDE.md, and

CI runs the same commands on each pull request.

Non-goals

  • A public hosted instance. The project stays self-hosted.
  • MeshCore or any mesh firmware other than Meshtastic.
  • Native Linux variants (meshtasticd, architecture native). Their output is not

flashable.

  • Over-the-air (OTA) firmware update.
  • Injection of a config into a prebuilt binary without a compile. No upstream mechanism

exists for it.

  • Accounts for operators. The admin password is the only sign-in.
  • The userPrefs keys USERPREFS_UI_TEST_LOG, USERPREFS_FIRMWARE_EDITION and

USERPREFS_MESH_BEACON_LEGACY_SPLIT. They are for upstream testing and vendor editions.

Cross-cutting concerns

Authentication and authorization (built). The admin password is a bcrypt hash in config.yaml. POST /admin/login sets the cookie mtfw_session: an itsdangerous signature of the string admin, HttpOnly, SameSite=Lax, max age 3600 s. The cookie sets Secure only when the request scheme is https. These routes require the session: /api/v1/update-firmware, /api/v1/cleanup, GET /api/v1/firmware/available, POST /api/v1/firmware/install and DELETE /api/v1/firmware/{version}. The /admin page shows a sign-in form when no session exists.

CSRF (built, Epic 3). Each admin form carries the hidden field csrf_token. The token is the value of the cookie mtfw_csrf, signed with the same itsdangerous secret key. Sign-in sets a new mtfw_csrf value, so the token belongs to one session. A JSON request and a DELETE request send the token in the header X-CSRF-Token. Each admin POST or DELETE without a valid token returns 403:

  • /admin/login
  • /admin/logout
  • /api/v1/update-firmware
  • /api/v1/cleanup
  • POST /api/v1/firmware/install
  • DELETE /api/v1/firmware/{version}

Planned auth changes (feature build-pipeline-repair):

  • Build ids are random, so one operator cannot guess another operator's build.

Validation. Today the routes read raw JSON. The pydantic models in models.py are not used. Planned: every route validates its body with a pydantic model, and every enum (region, modem preset, role, GPS mode) comes from one module that matches the upstream protobufs.

Errors. Today the config routes return HTTP 200 with success: false and the raw exception text. Planned: a validation error returns 422 with field errors. An internal error returns 500 with a generic message and logs the detail.

Secrets. A secret is never logged, never stored in the database, never kept in a cache entry, and never kept in browser storage after the page closes. The project scrubs the firmware source after every build. The build log sent to the page has every secret value replaced with ***.

Logging. Standard logging, optional JSON format (MTFW_LOG_JSON). No print().

Accessibility. Every input has a label. The progress stream region has aria-live="polite". Every icon-only button has an aria-label. Colors meet WCAG AA contrast in light and dark themes.

i18n. English only. Not planned.

Performance. One build worker by default (MTFW_BUILD_WORKERS, default 1). A PlatformIO build of one ESP32 variant takes several minutes on first build and uses several GB of disk for toolchains. The build cache returns a repeated build in under one second.

Security headers. nginx sets them in production (nginx/nginx.conf.example). The app sets none. Planned: the app sets X-Content-Type-Options, Referrer-Policy and a Content-Security-Policy that allows only vendored scripts.

Testing strategy

  • Unit: pytest, asyncio_mode = "auto". 106 tests at the inherit (2026-11-21, bd15bb1);

the suite grows with each epic.

  • Contract tests (planned): the userPrefs keys the generator writes are a subset of

the keys the fixture firmware source reads. The registry fixture matches pio project config --json-output output.

  • Integration (planned): route tests through httpx for every /api/v1 route,

including the progress stream. A fake pio executable stands in for PlatformIO.

  • E2E smoke (planned): Playwright loads each page, fills the config form, starts a

build against the fake pio, and downloads the artifact.

  • Real build (planned, manual or scheduled CI): one real pio run of one ESP32 and

one nRF52 variant.

  • A change is done when uv run pytest, uv run ruff check, and `uv run ruff format

--check pass, and the E2E smoke passes for any change under templates/ or static/`.

Assumptions

  • The repair targets the firmware version that releases/latest returns

(v2.7.26.54e0d8d on 2026-11-21). Firmware 2.8 support arrives with Epic 5.

  • Python 3.13 is the target runtime. Python 3.14 is possible, but the meshtastic

python package requires <3.15, and 3.13 gives more margin.

  • One build worker is the default. A homelab machine cannot run two ESP32 compiles at

once without heavy swap.

  • Builds by operators who are not signed in stay allowed. The instance is self-hosted

and trusted.

  • The fixture firmware source for tests is a hand-picked subset copied from upstream

under GPL-3.0, which the relicense allows.

  • Web Serial works only on HTTPS or localhost. The docs tell a LAN self-hoster to use

the nginx overlay with TLS.

  • The meshtastic.org/e/# channel URL format is stable across 2.7 and 2.8 firmware.
  • Reconstructed ADRs (0001–0003) record choices made in 2025–2026. Their context is

reconstructed from the code and commit log, not from records of the time.

Risks & open questions

Contradictions between documents and code (the code is the fact):

  1. README says 62 variants. The registry holds 150. The README is stale since commit

e575ce7.

  1. README links a LICENSE file. No LICENSE file exists. pyproject.toml says MIT.

Resolved in the interview: relicense to GPL-3.0 (ADR 0004).

  1. README says the database stores build history and profiles. No code reads or writes

the database.

  1. README says the frontend uses htmx. No template uses an hx- attribute.
  2. README describes real-time build progress. The build page never opens the progress

stream, and it calls v1 URLs.

  1. README says the admin panel needs the admin password. The page has no sign-in form.
  2. README says builds clean up after 1 hour. No periodic task exists.
  3. README says secrets are scrubbed from artifacts. Scrub runs on success only, and

.elf and object files keep the values.

  1. README says uploads are validated as JSON. Only size and UTF-8 are checked.
  2. CONTRIBUTING says the id must match a PlatformIO environment. 71 ids do not.
  3. pyproject.toml and CONTRIBUTING say Python 3.10+. The code needs 3.11

(asyncio.timeout, build_service.py:80).

  1. The README volume table names paths the app does not write to

(docker-compose.yml; see features/02-firmware-builder.md).

  1. docker.env.example and docker-deploy.sh cleanup use v1 names and routes.

Risks:

  • Router roles are not factory defaults. Upstream replaces a userPrefs role of

ROUTER, ROUTER_LATE or LOST_AND_FOUND with CLIENT (src/mesh/NodeDB.cpp:1180-1188). A fleet of routers needs push config (Epic 12) after the flash. Features 11 and 14 reject those roles with a clear message.

  • Secrets in build logs. Upstream bin/platformio-custom.py prints every -D

flag, and the flags hold PSKs and passwords. The progress stream sends the last 100 log lines. Mitigation: mask in feature 06.

  • Upstream churn. Upstream changes userPrefs keys, artifact names and toolchains

without notice. Mitigation: contract tests against the fixture firmware source, and a scheduled CI job against upstream develop.

  • JS client library in flux. meshtastic/js is archived. meshtastic-sdk JS is

"snapshot only until 0.3.0". Epic 12 starts with a spike to choose.

  • Disk use. Each firmware version plus its toolchains uses several GB. Mitigation: an

admin removes firmware versions from the firmware sources page.

  • ESP32 2.8 toolchain. Firmware 2.8 uses the pioarduino platform and fetches ESP-IDF

components at build time. Network errors fail builds. Mitigation: retry, as upstream bin/build-esp32.sh does.

Open questions: none block approval.
